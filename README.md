# sedori-board — せどり盤

勝てる商品が一目で分かって、玉が市場に出たら買いアラート、出口が動いたら売りアラートが飛ぶ盤。

```
pip install -r requirements.txt
streamlit run app.py          # サイト
python watch.py --loop 20     # アラート常駐(Discord)
```

## 何をする道具か

**収集も採点もせん。** ヤフオク収集も買取表退避も本文検品も工場も、全部
`C:\dev\souba-league` が既にやっとる。この盤はそれを読んで、
**「で、結局どれ買うんや」に1画面で答える**だけの層や。
収集ロジックを二重に持つと必ずズレるので、CSVのパス解決と列名の正規化しか持たん。

## 等級の付け方 — ここだけは譲らん

souba-league の個体検証(2026-08-03)で出た数字が全ての前提や:

| | 候補 | 本文検品を通った | 生存率 |
|---|---|---|---|
| カメラ(人手20件) | 20 | 3 | 15% |
| 楽器(人手18件) | 18 | 2 | 11% |
| 楽器(LLM全43件) | 43 | 5(黒字は1) | 12% |

つまり **タイトルフィルタの候補は85〜89%がゴミ**。しかも大スプレッドほどゴミが濃い
(良品の買取価格に腐った個体がマッチしとるから、スプレッドが大きく見える)。
so:

- **スプレッドで並べん。** 並べる軸は「本文検品を通った件数 × その粗利中央値」= `期待粗利180d`。
- **紙上WON(工場台帳)で等級を上げん。** あれは「max_bid で入札しとったら勝てたか」を
  見とるだけで、その個体が良品やったかは見とらん。バッジとしてだけ出す。
  **2026-08-07に実証**: 紙上で勝った6件を検品したら **kill 6 / keep 0**
  (紙上純利¥73,895 → 検品通過¥0)。負けは**惜敗ゼロ**(上限を中央+28%超過)で、
  つまり**勝てた玉は誰も競らんかった玉** = 逆選択。安く落ちるのは壊れとるからや。

| 等級 | 条件 | 意味 |
|---|---|---|
| 🟢 実弾GO | 検品通過1件以上 かつ 期待粗利180d ≥ ¥10,000 | 買え |
| 🟡 薄い | 検品は通ったが180日で1万円未満 | 月1,600円未満。手間に合わん |
| 🟣 標本不足 | 検品したが3件未満で全滅 | まだ死とは言えん。要追試 |
| ⚪ 未収集 | 180日の落札をまだ集めとらん | 唯一の「分からん」 |
| 🔵 玉が薄い | 本体の落札が180日で10件未満 | 検品以前に仕入れる玉が無い |
| ⚫ スプレッド無し | 本体が10件以上落ちたが安値が1件も出ん | 母集団は厚いのに立たん |
| 🔴 死 | 検品3件以上で全滅 | 母集団が腐っとる |

### 「流動性」を生の落札行で数えたら大嘘になる

`yahoo_closed.csv` はクエリのヒットを全部持っとって、X100V の行には互換バッテリーも
フードも混ざる。**生1,000行・落札中央¥9,999**(本体は¥18万)という有様や。
工場が実際に入札対象にする行だけを数えると **カメラ 15,971行 → 2,946行(18%)**、
X100V は **6件・中央¥198,950** になる。判定は `factory.title_ok` を借りる
(自前の正規表現を書いたら、工場と盤で「玉」の定義がズレる)。

### 盤の空白は「未検品」やない

192型番の内訳: 🟢4 / 🟡12 / 🟣22 / ⚪10 / 🔵89 / ⚫47 / 🔴8。
**未収集はたった10件**で、残り182件は既に結論が出とる。最大の壁は検品やのうて
**玉の供給**で、玉/180日の中央値は **6本(月1本)**、115/192型番が10本未満や。

### 判定器の出所を必ず見ろ

同じCSVでも判定器で結論が変わる。人手38件を正解ラベルにした実測:

| 判定器 | 撃墜の再現率 | 生存側の精度 |
|---|---|---|
| regex | 高い(15-16/17) | **カメラ3件中1件しか残せず(致命的)** |
| LLM(Groq) | 同等 | 4件中3件を正しく残す |

生存率が1割の世界では**生存側の精度が命**。実際 regex版のカメラCSVで採点すると
XF56mm と ES35100 が🔴に落ちる — 人手検証が生存と判定した、まさにその2型番や。
盤は `candidates_llm.csv` を優先して読み、regex版しか無いときは画面に警告を出す。

最終権限は人間にある。実物ページを見て覆した判定は `data/human_verdicts.csv` に
`auction_id,verdict` を書けば、LLMの判定を上書きする。

## アラート

**買い** — 工場が発火した進行中ヤフオク。ただし工場は等級を見とらんので盤で貼り直す:
- 🔴 の型番は握り潰す(腐っとると分かっとる母集団に実弾を入れる理由が無い)
- 上限入札を既に抜かれた個体は落とす(もう買えん)
- 「本文を検品」ボタンで**進行中個体の説明文**を読む。判定器は verify_body のものを
  そのまま借りる(別実装を持つと精度の根拠が消える)。`watch.py` は自動で検品して、
  撃墜なら通知せん

**売り** — 買取表の日次スナップ差分(¥2,000 かつ 3% 以上を変化とみなす)。
- 📉 下落 = 出口の悪化。保有分は急いで出す
- 📈 上昇 = その型番の裁定窓が開いた。上限入札も自動で上がる

`data/holdings.csv` に保有玉を書けば、最新の買取表で毎日評価して売り時を出す。

### 拡大の余地(2026-08-07時点)
検品済み46型番のうちGOは4 = **GO率8.7%**。未解決は 🟣22 + ⚪10 = 32型番やから、
同じ率が続くとして期待は **+2.8型番 ≒ +¥50,000/180日**。今の¥67,200と足して月¥20,000弱。
しかも🟣22は一度検品して落ちとる母集団やから、これは**上限**として読むべきや。

→ **型番を増やす道はほぼ塞がっとる。** 伸ばすなら (a) 新しい買取源
(じゃんぱら・駿河屋・島村 = souba-league/docs/loop_candidates.md でS/SSR判定済み)か
(b) 別カテゴリしかない。

## 燃料の補給

盤が古い数字を出すのは玉が無いからやのうて、上流が止まっとるからや。「🏭 稼働」タブで見る。

```
cd C:\dev\souba-league
python src/factory.py --loop 30      # カメラ工場(買いシグナルの源)

       --out data/camera/candidates_llm.csv --llm    # 等級の源
```

## streamlit.app へのデプロイ

クラウドには `C:\dev\souba-league` が無い。生データも積めん(キタムラ買取表は1枚6MB、
ヤフオク落札は16MB)。なので **`export_snapshot.py` が計算済みの結果だけを
`data/snapshot/` に落とし、クラウドのアプリはそこしか読まん**(合計190KB程度)。

```
python export_snapshot.py     # ← push する前に必ず1回
git add -A && git commit -m "snapshot YYYY-MM-DD" && git push
```

`core/sources.py` の `CLOUD = not SOUBA.exists()` で自動的に切り替わる。
判定器(`verify_body.py` / `find_winners.py` / `spread_camera.py`)は
エクスポータが `core/vendor/` にコピーする——**原本は souba-league/src で、
vendor はビルド成果物。直接編集したらあかん。**

クラウドで生きとる機能・死んどる機能:

| | クラウド | 理由 |
|---|---|---|
| 買い物リスト・型番マスタ・台帳・墓場 | ○ | スナップショットに入っとる |
| 買い/売りアラート | △ **断面** | push した時点の値。リアルタイムやない |
| 進行中個体の「本文を検品」ボタン | ○ | その場でヤフオクを見に行くので生きとる |
| 保有玉の評価 | ✗ | 買取表の実物が要る。ローカルのみ |
| `watch.py`(Discord常駐) | ✗ | ローカルで回すもの |

合言葉は Streamlit Cloud の Settings → Secrets に `PASSWORD = "..."` を置く。
ローカルは secrets が無いので素通しで開く。
