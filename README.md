# sedori-board — せどり盤

勝てる商品が一目で分かって、玉が市場に出たら買いアラート、出口が動いたら売りアラートが飛ぶ盤。

```
pip install -r requirements.txt
streamlit run app.py          # サイト
python watch.py --loop 20     # アラート常駐(Discord)
```

## 何をする道具か

**収集も採点もせん。** ヤフオク収集も買取表退避も本文検品も工場も、全部
`C:\dev\souba-league` が既にやっとる。この盤はそれを読んで、
**「で、結局どれ買うんや」に1画面で答える**だけの層や。
収集ロジックを二重に持つと必ずズレるので、CSVのパス解決と列名の正規化しか持たん。

## 等級の付け方 — ここだけは譲らん

souba-league の個体検証(2026-08-03)で出た数字が全ての前提や:

| | 候補 | 本文検品を通った | 生存率 |
|---|---|---|---|
| カメラ(人手20件) | 20 | 3 | 15% |
| 楽器(人手18件) | 18 | 2 | 11% |
| 楽器(LLM全43件) | 43 | 5(黒字は1) | 12% |

つまり **タイトルフィルタの候補は85〜89%がゴミ**。しかも大スプレッドほどゴミが濃い
(良品の買取価格に腐った個体がマッチしとるから、スプレッドが大きく見える)。
so:

- **スプレッドで並べん。** 並べる軸は「本文検品を通った件数 × その粗利中央値」= `期待粗利180d`。
- **紙上WON(工場台帳)で等級を上げん。** あれは「max_bid で入札しとったら勝てたか」を
  見とるだけで、その個体が良品やったかは見とらん。バッジとしてだけ出す。
  **2026-08-07に実証**: 紙上で勝った6件を検品したら **kill 6 / keep 0**
  (紙上純利¥73,895 → 検品通過¥0)。負けは**惜敗ゼロ**(上限を中央+28%超過)で、
  つまり**勝てた玉は誰も競らんかった玉** = 逆選択。安く落ちるのは壊れとるからや。

| 等級 | 条件 | 意味 |
|---|---|---|
| 🟢 実弾GO | 検品通過1件以上 かつ 期待粗利180d ≥ ¥10,000 | 買え |
| 🟡 薄い | 検品は通ったが180日で1万円未満 | 月1,600円未満。手間に合わん |
| 🟣 標本不足 | 検品したが3件未満で全滅 | まだ死とは言えん。要追試 |
| ⚪ 未収集 | 180日の落札をまだ集めとらん | 唯一の「分からん」 |
| 🔵 玉が薄い | 本体の落札が180日で10件未満 | 検品以前に仕入れる玉が無い |
| ⚫ スプレッド無し | 本体が10件以上落ちたが安値が1件も出ん | 母集団は厚いのに立たん |
| 🔴 死 | 検品3件以上で全滅 | 母集団が腐っとる |

### 「流動性」を生の落札行で数えたら大嘘になる

`yahoo_closed.csv` はクエリのヒットを全部持っとって、X100V の行には互換バッテリーも
フードも混ざる。**生1,000行・落札中央¥9,999**(本体は¥18万)という有様や。
工場が実際に入札対象にする行だけを数えると **カメラ 15,971行 → 2,946行(18%)**、
X100V は **6件・中央¥198,950** になる。判定は `factory.title_ok` を借りる
(自前の正規表現を書いたら、工場と盤で「玉」の定義がズレる)。

### 盤の空白は「未検品」やない

192型番の内訳: 🟢4 / 🟡12 / 🟣22 / ⚪10 / 🔵89 / ⚫47 / 🔴8。
**未収集はたった10件**で、残り182件は既に結論が出とる。最大の壁は検品やのうて
**玉の供給**で、玉/180日の中央値は **6本(月1本)**、115/192型番が10本未満や。

### 判定器の出所を必ず見ろ

同じCSVでも判定器で結論が変わる。人手38件を正解ラベルにした実測:

| 判定器 | 撃墜の再現率 | 生存側の精度 |
|---|---|---|
| regex | 高い(15-16/17) | **カメラ3件中1件しか残せず(致命的)** |
| LLM(Groq) | 同等 | 4件中3件を正しく残す |

生存率が1割の世界では**生存側の精度が命**。実際 regex版のカメラCSVで採点すると
XF56mm と ES35100 が🔴に落ちる — 人手検証が生存と判定した、まさにその2型番や。
盤は `candidates_llm.csv` を優先して読み、regex版しか無いときは画面に警告を出す。

最終権限は人間にある。実物ページを見て覆した判定は `data/human_verdicts.csv` に
`auction_id,verdict` を書けば、LLMの判定を上書きする。

## アラート

**買い** — 工場が発火した進行中ヤフオク。ただし工場は等級を見とらんので盤で貼り直す:
- 🔴 の型番は握り潰す(腐っとると分かっとる母集団に実弾を入れる理由が無い)
- 上限入札を既に抜かれた個体は落とす(もう買えん)
- 「本文を検品」ボタンで**進行中個体の説明文**を読む。判定器は verify_body のものを
  そのまま借りる(別実装を持つと精度の根拠が消える)。`watch.py` は自動で検品して、
  撃墜なら通知せん

**売り** — 買取表の日次スナップ差分(¥2,000 かつ 3% 以上を変化とみなす)。
- 📉 下落 = 出口の悪化。保有分は急いで出す
- 📈 上昇 = その型番の裁定窓が開いた。上限入札も自動で上がる

`data/holdings.csv` に保有玉を書けば、最新の買取表で毎日評価して売り時を出す。

### 拡大の余地(2026-08-07時点)
検品済み46型番のうちGOは4 = **GO率8.7%**。未解決は 🟣22 + ⚪10 = 32型番やから、
同じ率が続くとして期待は **+2.8型番 ≒ +¥50,000/180日**。今の¥67,200と足して月¥20,000弱。
しかも🟣22は一度検品して落ちとる母集団やから、これは**上限**として読むべきや。

→ **型番を増やす道はほぼ塞がっとる。** 伸ばすなら (a) 新しい買取源
(じゃんぱら・駿河屋・島村 = souba-league/docs/loop_candidates.md でS/SSR判定済み)か
(b) 別カテゴリしかない。

来とるのに、候補づくりと本文検品が **8/07から一度も回っとらんかった**(定期実行が
無い)。焼き直した結果:

| 期待粗利180d | ¥36,100 | **¥167,936** |
| 🔴 死 | 13 | 18 |
| ⚫ スプレッド無し | 101 | 95 |

新GO: COOLPIX P900 / DC-FZ85 / RX100M2 / RX100M7 / FDR-AX700 / Martin 000-28 /
NEX-VG20。**GOから落ちた型番はゼロ。**

再発防止に週次タスク `souba-rebuild-grades-weekly`(日曜03:00)を登録した。
落札は新しい順に返るので `--max-pages 3` で差分が取れる(実測)。

### 焼き直しの前に、判定器が死んどった

Cerebras(主)が **HTTP 402**(`Payment required ... Visit your billing tab`)、
Groq(控え)は既定モデル `llama-3.3-70b-versatile` が `/v1/models` から消滅済み。
**カスケードが主も控えも全滅**しとった。

さらに悪いのがコードの形で、402 は `error` を返し、`error` は while を break する
= **主が死んだ瞬間に控えを一度も呼ばず、全件が黙って正規表現に退避**する。
出力先は `candidates_llm.csv` のままやから、盤は「判定器: LLM」と名乗り続ける。
正規表現は生存側の精度が致命的(カメラ3件中1件しか残せん)やから、
**等級が黙って劣化して名乗りだけ残る**形や。

- `401/402/403/404` を `dead` として `error` と分けた(次の1件で直ることは無い)
- `dead`/`error` でカスケードを諦めず**次のプロバイダに下りる**
- 控えを **Cerebras の主と同じ `openai/gpt-oss-120b`** に差し替え。
  ホストだけ替えて**判定器は替えん**(判定器が変われば等級の比較可能性が消える)
- 盤の「判定器」は**ファイル名やのうて中身で数える**。`body_hit` の `(regex退避)`
  接頭辞を数えるので、スキーマを変えず過去のファイルも測れる

歴史の等級は無事やった(8/07の検品は退避 0/62 と 4/159 で本物のLLM判定)。
危なかったのは**次の再検品**のほうや。

### 「生存件数」は「機会の数」やない

NEX-VG20 の生存3件は、全部 **2026-08-31 終了・M1013/M1014/M1015 の連番・
同一テンプレ** = 1出品者のまとめ放出やった。盤はそれを 3件×¥3,520=¥10,560 と
読んで GO閾値¥10,000 をギリギリ越えとる。実際の機会は1件で🟡薄いや。

`生存日数`(生存した玉の終了日が何日に散っとるか)と `束の疑い` を足した。
**等級は黙って動かさん** — 数字を勝手に割ると、割り方が正しかったかを後から
検算できんようになる。旗を立てて読み手に割り引かせる。全381型番で旗が立つのは
この1件だけやった。

## 鮮度の門 — 「在るか」やのうて「止まっとらんか」

2026-09-08まで🏭稼働タブの `状態` は `p.exists()` しか見とらんかった。
**止まっても永久に「生存」と出る門**やから、止まっとるのに気づかせるという
目的をそもそも果たしてへん。その日の実測で、**等級の土台である検品結果2枚が
32日古いまま「生存」**と表示されとった。souba-league では同じ穴でキタムラ買取が
**29日**死んで、上書き型やからその断面は永久に取り返せん。

門は2つ要る。**片方だけでは検品結果の死が見えん**:

| 門 | 中身 | 何を捕まえるか |
|---|---|---|
| **周期** | 定期実行の間隔の1.5倍で ⏳遅延、3倍で 🚨停止 | 常駐が落ちた源。閾値は `souba-league/docs/scheduled.md` の実際の登録間隔から取る(こっちで発明せん) |
| **依存** | 派生物は入力より新しいはず。古かったら 🚨入力よりN日古い | **定期実行が無い源**。検品結果は落札から作るのに落札より古い=新しく落ちた玉が1件も採点に入っとらん |

土台(`土台=True`)が止まったら **盤の頭に赤を出す**。9枚目のタブに埋めたら誰も見ん。
`export_snapshot.py` も publish のログに吠える(**止めはせん**——publish を止めたら
盤ごと古くなるだけで事態が悪化する)。

両方向を実測してある: 生きとる源の mtime を巻き戻すと 生存→⏳遅延→🚨停止 と動き、
戻すと緑に返る。検品結果を落札より新しくすると赤が消える。**片側だけ確かめたら
「常に赤」の門と見分けが付かん。**

### 古さを金額で測った(2026-09-08)

「古い」だけでは動く理由にならんので、いくら見落としとるかを数えた。
落札(9/01基準)から候補を焼き直すと **wide帯 96→156件、うち66件が8/07の検品に
入っとらん**。窓は90/96重なっとるので、これは**窓の進みやのうて純増**や。

粗利¥3,000以上に絞ると **28件・12family・机上¥521,516**。実測の生存率14.9%を
掛けて **期待¥77,706** — いま盤が出しとる実弾GO 3型番の **¥36,100** より大きい。
**ただし逆選択があるから上振れ側の見積もりで、検品を通すまでは机上や。**

🚨 **焼き直しは帯ごとに `--models` / `--yahoo` / `--out` を揃えること。**
`spread_camera.py` の既定引数は **base帯**(`models/camera.csv`)やのに、
等級が乗っとる `data/camera/candidates.csv` は **wide帯**の産物や。
既定のまま回すと**別の母集団で静かに上書きする**——実際、それで比べた最初の差分は
「96件中94件が消えた」いう嘘の数字が出た。正しいコマンドは🏭稼働タブに出しとる。

### 🚨 門は直したのに、盤は4.5日凍っとった(2026-09-22)

鮮度の門を2枚建てた9日後に、**盤(streamlit.app)が 9/17 15:20 の断面を
4.5日出し続けとった**のが出てきた。門の話やない。**公開の話**や。

| | |
|---|---|
| 家の工場 | 生きとった。3時間おきに走査→検品→検査→出力を35回まわしとる |
| 家の断面 | 生きとった。`data/snapshot` は毎回ちゃんと書き変わっとる |
| **公開** | **35回ぜんぶ `git push` が弾かれとった** |

原因は**枝が分かれとった**こと。クラウド側で盤の直しが8本 origin に入っとって、
家は遅れとる。`publish.py` は `git push` を素で叩くだけやから `fetch first` で
弾かれる。弾かれたら「push が通らんかった。」と**1行だけ**ログに書いて終いや。

**誰にも届かん失敗は、失敗せんのと同じに見える。**

- `logs/publish.log` に35行出とったが、あれは**1.1MB のログの底**や
- タスクの `LastTaskResult` は **1** のままやった。**RC を読む常駐が無い**
- 盤の画面は普通に開く。中の数字だけが4日半前のもんや

直したのは `souba-league/src/publish.py` の公開ブロック:

1. **弾かれたら `pull --rebase` して3回までやり直す。** ここが commit するのは
   `data/snapshot` と `core/vendor` の**生成物だけ**やから、向こうの直しの上に
   rebase して構わん(取り合う行が無い)
2. **`git add -A` をやめた。** 盤のツリーは別のセッションも触る。`-A` やと
   向こうの書きかけを巻き込んで公開してまう
3. **通らんかったら Discord に吠える**(`FACTORY_WEBHOOK_URL`)

#### 分かれとる間、クラウド側は「手順が飛んだ」と読んどった

向こうは 9/21 に同じ症状(89時間前の写真)を見て、`run_snapshot.bat` という
**手で叩くボタン**を足しとった。クラウドからは家のタスクもログも見えんから、
「export が9/17から回っとらん」と読むしかない。**実際は回っとって、push だけが
死んどった。** 症状が同じでも、**どっちが止まったかを名指しできん場所から
診断すると、直しが効かん場所に置かれる**。ボタンは残す(手で入れ替えたい時に要る)。

#### 直す場所は型番やのうて、定義が2箇所あることやった

`souba-league/models/gakki_factory.csv`(**実弾を撃つ側**)には
**最初から正しい式が入っとった**:

```
買い側 : (?=.*(?:三響|SANKYO|サンキョウ))(?=.*(?:ハンドメイド|HAND\s?MADE))
         除外: ETUDE|エチュード|ARTIST|アーティスト|PRIMA|プリマ|SILVER SONIC|エスプリ
等級側 : 三響|SANKYO        ← 除外なし
```

**11 family で両者が分かれとって、分かれ方は全部片方向**——買い側だけが
手で締めてあった。**買い側で正しい答えが出とっても、等級はそれを読んどらん。**

さらに悪いのが列の方で、買い側にある `require_re` / `maker_re`(ムラマツの
EX/GX/DS の識別、Gibson/Martin/PRS のメーカー名要求)は
**等級側の `models/gakki.csv` にそもそも列が無かった**。
`spread_gakki.py` は両方を読む造りやのに `r.get("require_re")` が None を返して、
**門が黙って開いとった**——**欠損が有利側に化ける**形や。

- 締めた式11本を生成器(`make_gakki_models.BASKET`)と `models/gakki.csv` に戻した
- ac30hw と axefx3_mk2 を締め直した。**入れる前に両側を測る**:
  ac30hw は落札1,013行から**本物4行だけ通過・誤爆0**、axefx3 は1,137行から0行
- 🚨 `make_gakki_factory.py` が `require_re`/`maker_re` を `""` で書いとって、
  **手で足した門12本を regenerate 一発で消した**(この作業中に踏んだ)。
  門は生成器の中に置く

## streamlit.app へのデプロイ

クラウドには `C:\dev\souba-league` が無い。生データも積めん(キタムラ買取表は1枚6MB、
ヤフオク落札は16MB)。なので **`export_snapshot.py` が計算済みの結果だけを
`data/snapshot/` に落とし、クラウドのアプリはそこしか読まん**(合計190KB程度)。

```
run_snapshot.bat              # ← 普段はこれ1個でええ
```

`run_snapshot.bat`(中身は `push_snapshot.py`)が pull → export → 鮮度の確認 →
commit → push まで通しでやる。**3を飛ばしたらあかんのがミソ**で、export は
souba-league が今持っとるもんを写すだけやから、**工場が止まっとったら古い数字を
そのまま写す**。写した直後に何が死んどるか名指しする(2026-09-21に、盤が
89時間前の写真を出しとるのに鮮度の門が0件やった件)。

手でやるなら:

```
python export_snapshot.py     # ← push する前に必ず1回
git add -A && git commit -m "snapshot YYYY-MM-DD" && git push
```

`core/sources.py` の `CLOUD = not SOUBA.exists()` で自動的に切り替わる。
判定器(`verify_body.py` / `find_winners.py` / `spread_camera.py`)は
エクスポータが `core/vendor/` にコピーする——**原本は souba-league/src で、
vendor はビルド成果物。直接編集したらあかん。**

クラウドで生きとる機能・死んどる機能:

| | クラウド | 理由 |
|---|---|---|
| 買い物リスト・型番マスタ・台帳・墓場 | ○ | スナップショットに入っとる |
| 買い/売りアラート | △ **断面** | push した時点の値。リアルタイムやない |
| 進行中個体の「本文を検品」ボタン | ○ | その場でヤフオクを見に行くので生きとる |
| 保有玉の評価 | ✗ | 買取表の実物が要る。ローカルのみ |
| `watch.py`(Discord常駐) | ✗ | ローカルで回すもの |

合言葉は Streamlit Cloud の Settings → Secrets に `PASSWORD = "..."` を置く。
ローカルは secrets が無いので素通しで開く。
